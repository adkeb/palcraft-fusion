# Initial target authoritative snapshot pending lease

Two existing frozen candidate21 protocol payloads receive the same small error-loop change. A current proof with `authoritative_snapshot_pending` is admitted to the original finite progress calculation only when its already-validated actual snapshots_pending integer is positive. A completed original companion bootstrap no longer blocks this separate legitimate stage.

No count, seq, ready flag, target, bounds, pose, or ACK is created. The existing current-ticket identity/generation, companion-bootstrap consistency, real revision/pending-count/coverage progress, unchanged clocks and finite caller cap remain intact. An unfinished companion bootstrap still requires its original scanned/completed progress. Pending alone cannot renew indefinitely. Landing50cm, native camera750ms and the normal complete/ACK path are untouched.

`checks/check_lease.lua` runs four bounded source cases using explicitly synthetic proof/ticket/time tables. It loads the actual old and new modules. Cases verify pending count reduction with completed bootstrap, no-progress/zero-pending/other-error/cap rejection, stale native/owned tuple rejection, and original bootstrap behavior equivalence. These are source-contract cases, not real Game or first-target42 acceptance. All four passed in one actual Lua5.4 run.

Run `lua checks/check_lease.lua DELTA_ROOT`. No dependencies or runtime components are added. The candidate21 manifest contains exactly two existing travel/protocol payload targets; its outer wrapper has none. No third role/target was invented. Actual42's failure proof was absent, so this fixes the verified source admission gap without claiming it was the only real failure cause.
